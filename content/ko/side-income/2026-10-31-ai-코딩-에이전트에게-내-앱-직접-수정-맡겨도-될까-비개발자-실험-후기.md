## AI 코딩 에이전트, 지금 어디까지 왔나

2025년 2월, OpenAI 초기 멤버 Andrej Karpathy가 X에 "바이브 코딩(vibe coding)"이라는 개념을 올렸어요. 코드를 직접 쓰는 대신 AI에게 "이런 느낌으로 만들어줘"라고 말하는 방식이에요. Collins 사전이 이걸 2025년 올해의 단어로 선정할 정도였으니까요.

2026년 지금은 실험실 밖으로 완전히 나왔어요. Replit, Cursor, Lovable이 경쟁적으로 기능을 늘리고, 6월엔 OpenAI가 Codex 기반의 **Sites** 기능을 내놓으면서 판이 더 촘촘해졌어요. AI 코딩 에이전트는 이제 단순히 코드를 생성하는 게 아니라 파일을 읽고, 테스트를 실행하고, 패키지를 설치하고, 배포 스크립트까지 자율적으로 처리해요. 사람 없이도 상당 부분 돌아가는 자율 실행자에 가깝죠.

그럼 비개발자가 자기 앱에 이걸 붙이면 실제로 어떻게 될까요? MIT Technology Review Korea가 소개한 비개발자 콘텐츠 제작자의 1개월 실험이 꽤 솔직해요.

- **영어 더빙 자동화** (TTS 기반): 직접 만들어 씀
- **망가진 브라우저 플러그인 복원**: 업데이트 이후 호환성 문제 직접 해결
- **맞춤형 일정 관리 도구**: 기존에 없던 소프트웨어를 직접 구현

세 개 모두 성공했어요. 근데 월 28만 원(200달러)이 나갔고, 뭐든 만들 수 있다는 가능성이 역설적으로 할 일 목록을 폭발적으로 늘려버리는 부작용도 생겼대요.

## AI에게 맡겨도 되는 것 vs. 절대 안 되는 것

[Jestools Brief의 2026 위험 체크리스트](https://jestools.com/posts/ai-coding-agent-dangerous-tasks-checklist-2026/)는 OpenAI, Anthropic, GitHub, OWASP 문서를 기반으로 **7가지 절대 금지 영역**을 정리했어요. AI 에이전트가 자율 실행자로 진화할수록 이 경계선이 더 중요해지거든요.

| 작업 영역 | AI에게 맡겨도 되는 범위 | 사람이 직접 해야 할 범위 |
|---|---|---|
| **API 키·보안 자격증명** | `.env.example` 템플릿 초안 작성 | 실제 키 입력·교체·폐기 |
| **프로덕션 DB 조작** | 마이그레이션 SQL 초안, 롤백 계획 작성 | 백업 확인, 스테이징 검증 후 실행 |
| **파괴적 셸 명령** | 삭제 후보 목록 생성 | `rm -rf`, `chmod -R` 직접 실행 |
| **인증·권한 로직** | 코드 초안 작성 | 로그인 플로우·JWT·결제 웹훅 보안 검토 |
| **법적·라이선스 결정** | 관련 문서 위치 파악 | GPL 호환성, GDPR 준수 여부 판단 |
| **의존성 패키지 변경** | 패키지 2-3개 비교 초안 | 메이저 버전 업그레이드 최종 승인 |
| **장애 대응** | 로그 요약 | 서버 재시작·DB 페일오버·보안 키 폐기 |

원칙은 간단해요. **읽기 권한은 넓게, 쓰기·삭제·배포·보안 키 접근은 좁게.** AI가 초안을 만들고, 사람이 최종 실행을 승인하는 구조가 지금 권장하는 기준선이에요.

반면 AI가 확실히 잘하는 영역도 있어요. 테스트 디버깅, 반복 리팩토링, 문서 초안, 단순 UI 컴포넌트, 코드 리뷰 체크리스트, 마이그레이션 위험도 분석 같은 작업이요. 이 영역에선 거침없이 맡겨도 돼요.

## 데모에서 실제 서비스까지, 벽은 어디에 있나

비개발자가 AI로 앱을 만들다 보면 처음엔 놀라워요. 빠르게 뭔가 동작하거든요. 문제는 그 이후예요.

[Replit의 분석](https://jjeongil.tistory.com/3459)에 따르면, AI가 만든 앱이 실제 서비스로 넘어갈 때 가장 많이 무너지는 지점은 이렇게요.

- **로그인**: 권한 처리가 허술해서 다른 사용자 데이터에 접근 가능
- **데이터 저장소**: 로컬이나 임시 DB를 써서 개인정보가 엉뚱한 곳에 저장
- **API 키**: 설정 파일에 하드코딩되어 키 유출·요금 폭탄
- **결제 플로우**: 테스트 환경만 통과하고 실제 환불·웹훅 처리 실패
- **배포**: 로컬에서만 동작하고 공개 환경에서 취약점 노출

Replit이 Project Security Center에서 의존성 취약점 스캔을 제공하긴 하지만, 이건 출발점이지 완전한 해답이 아니에요.

**그럼 프롬프트는 어떻게 써야 할까요?**

실제로 효과 있는 방식이 있어요. 바로 만들어달라고 하기 전에 이렇게 먼저 물어보게 하는 거예요.

> *"코딩 전에 빠진 요구사항을 나한테 먼저 물어봐. 그다음 MVP 범위를 정리하고, 로컬에서만 검증 가능한 첫 번째 버전부터 만들어."*

AI가 코드를 생성하기 전에 의도를 먼저 정리하도록 유도하는 패턴이에요. Replit이 핵심 한계로 꼽은 게 코드 생성 능력이 아니라 **사용자 의도를 정확하게 읽는 것**이라는 점에서, 이 순서 하나가 결과를 꽤 많이 바꿔요.

## 비개발자라면 어디서 시작할까

Replit의 추천 기준을 빌리면, 비개발자가 AI 코딩 에이전트로 시작하기 좋은 타깃은 **한 달에 세 번 이상 반복되는 개인적인 불편함**이에요. 처음부터 상업용 SaaS를 만들겠다고 큰 그림을 그리면 문제 정의가 복잡해지고, AI가 의도를 잘못 읽을 가능성이 높아져요.

비용 현실도 봐야 해요. MIT Technology Review Korea 실험에서 월 28만 원이 나왔어요. 이 비용이 실제로 만들어낸 가치보다 크면 재고가 필요하죠.

참고로, 같은 도구가 누구에게나 열려 있다는 건 경쟁 우위가 빠르게 사라진다는 뜻이에요. AI 에이전트로 만들었다는 것 자체가 차별점이 되던 시대는 이미 지나갔어요.

## 지금 당장 챙겨야 할 것들

- AI 코딩 에이전트는 **초안 생성자**이지 **최종 실행자**가 아니에요. 이 원칙 하나가 사고를 막아요.
- 보안 5개 영역(로그인·데이터 저장·API 키·결제·배포)은 AI 결과물을 그대로 쓰지 말고, 반드시 사람이 확인해야 해요.
- 시작은 작게. 한 달에 세 번 이상 불편한 개인 문제부터 풀어보는 게 현실적이에요.
- 숙련된 개발자도 AI 도구를 쓰면 작업 시간이 19% 늘어날 수 있어요. 기대치 조정이 먼저예요.

앞으로 6~12개월 사이에는 에이전트가 보안 검토까지 일부 자동화하는 방향으로 발전할 거예요. OpenAI Sites, Replit, Cursor 간 경쟁이 격해질수록 비개발자가 쓸 수 있는 레이어는 점점 높아지겠죠.

그런데 결국 남는 질문은 이거예요. AI가 만든 앱이 실제로 돌아갈 때, 그 책임은 누가 지나요? 도구가 아무리 좋아져도, 이 질문에 답할 수 있는 사람이 루프 안에 있어야 해요.

지금 고민 중인 앱이 있다면, 먼저 어느 부분을 AI에게 맡길지 체크리스트로 정리해보세요. Jestools의 7가지 금지 영역 체크리스트가 그 시작점으로 딱 맞아요.
